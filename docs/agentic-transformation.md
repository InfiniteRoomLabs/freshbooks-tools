# Agentic transformation

How this repo gets built: pulling FreshBooks' own documentation data instead of writing it by hand, turning that into a machine-checkable contract, and running an agent pipeline against that contract phase by phase.

## Where the collection came from

FreshBooks publishes a Postman collection documenting its REST API. It was pulled with:

```
https://documenter.gw.postman.com/api/collections/3322108/S1ERwwza?segregateAuth=true&versionTag=latest
```

That is Postman's public "view collection as JSON" export URL for FreshBooks' own published documentation (collection id `3322108`, slug `S1ERwwza`) -- no scraping, no authentication, just the same JSON a browser gets when you open the collection's public documentation page. The file is committed at `freshbooks/internal/inventory/testdata/freshbooks.postman_collection.json`.

It holds 213 leaf requests across 14 top-level folders, with 22 subfolders nested one level deeper -- see the `STATE AS OF` callout in design spec section 3 for the exact counts and how they were verified against the earlier "130 requests" premise.

## Why no codegen

The collection has no response schemas, only example responses. Generating Go types from those examples would produce type-thin code that still needs a full rewrite once the real shape of optional fields, enums, and error paths is understood -- so the collection is a work-order source, not a code source. Every method in the library, every MCP tool, and every CLI command is handcrafted.

## The inventory tool

`freshbooks/internal/inventory` (`go run ./internal/inventory -in <collection> -out inventory.json`) walks the collection and normalizes each request into an `Entry`:

- **Key**: the full path `<Folder>/<Subfolder>/.../<Request name>`, every segment trimmed (the source has a folder literally named `My Team ` with a trailing space).
- **pathTemplate**: the URL path with Postman `{{variables}}` lower-camel-cased (`{{accountid}}`/`{{accountId}}`/`{{AccountID}}` all become `{accountId}`), hard-coded example IDs replaced with `{accountId}`/`{businessId}`/`{id}`, and `my.freshbooks.com/service/api/...` rewritten to its public `api.freshbooks.com` path.
- **family**: which of the API's families (`accounting`, `business`, `auth`, `events`, `uploads`, `payments`, `ledger`, `internal`, `unknown`) the request belongs to, by path prefix.
- Query params, request body, and example responses copied through for reference.

Two source requests can share a name (the collection reuses "Single Tax" for both a GET and a DELETE in two folders) -- these are genuine name collisions, not duplicates, so the tool disambiguates every side of the collision with a `" (METHOD)"` suffix (`Single Tax (GET)`, `Single Tax (DELETE)`) rather than silently dropping data, refusing to run, or letting collection order decide which request keeps a bare, ambiguous key.

The committed `testdata/inventory.json` is regenerated by re-running the command above; a golden test asserts it comes out byte-identical.

## The parity contract

`go run ./internal/inventory -check ./...` scans Go source for comments matching `// inventory: <key>`, and cross-references every key in `inventory.json` against them plus an ignore/todo list (`testdata/ignore.list`):

- `//go:inventory-ignore <key> -- <reason>` -- deliberately never implemented, with evidence in the reason (a hard-coded-ID duplicate of another request, or an endpoint confirmed dead). Phase 0's list has zero of these: the three requests hosted on `my.freshbooks.com` looked like internal aliases at first glance, but they turned out to be the *only* create-journal-entry, delete-project, and delete-subscription operations in the whole collection, so they're `todo` (pending live verification of the public host) rather than permanently `ignore`d.
- `//go:inventory-todo <key> -- <phase>` -- planned for a specific later phase; counts as covered now, reported separately so nothing is silently forgotten.

Every key must land in exactly one bucket. An uncovered key, a key with two competing `// inventory:` comments, a key that's both ignore/todo-listed *and* implemented, or a comment referencing a key that doesn't exist at all -- each fails the check. This same contract is what the MCP server and CLI parity tests check against once they exist, so "does this cover the whole API surface" has one answer instead of three.

## Work orders and the review gate

Each phase of work is dispatched from a written work order (`docs/phases/<n>/plan.md`, generated from `docs/phases/_templates/implementer.md`) with read-first pointers into the design spec rather than pasted context. Implementation is TDD, one branch per phase, gated before merge by four parallel-then-sequential review lanes -- code review, simplification, and security run read-only in parallel, then a QA lane runs the actual `mise run check` gate -- with findings triaged into one fix commit before merge. See design spec section 9 for the full process and `docs/phases/_templates/` for the templates themselves.

## The GOAL.md treadmill

`GOAL.md` holds exactly one phase's goal at a time: verify the premise against the spec and the real API/collection, implement, run the gate, ship, then retarget the file to the next phase. `docs/progress.md` is the human-readable handoff artifact -- current state, what's next, how to resume -- updated at every phase boundary.
