## A1 -- BLOCKING -- the pnpm hardening never applied; 18 locked versions are inside the 7-day quarantine window

`site/pnpm-lock.yaml` (whole file), `site/pnpm-workspace.yaml:1-18`, `docs/phases/10/plan.md:5,11`, `docs/phases/10/reports/implementer.md:24,29`

### What is wrong

pnpm 11 reads pnpm-specific settings from `pnpm-workspace.yaml`, **not** from `.npmrc`. The machine-wide hardening lives in `~/.npmrc` and `~/.config/pnpm/rc`, so under pnpm 11.15.1 every one of these keys is dead: `minimum-release-age`, `minimum-release-age-strict`, `block-exotic-subdeps`, `trust-policy`, `strict-dep-builds`, `verify-store-integrity`, `strict-store-pkg-content-check`, `prefer-frozen-lockfile`, `verify-deps-before-run`, `package-manager-strict`, `strict-peer-dependencies`, `auto-install-peers`.

The plan asserts the opposite (`plan.md:5`: "pnpm 11.15.1 (mise-managed) with the machine-wide hardening (`minimum-release-age=10080` strict, ...)"; `plan.md:11`: "First `pnpm install` will fail loudly under the machine policy"), and the implementer report repeats it (`implementer.md:29`: "No `dangerously-allow-all-builds`, no `minimum-release-age` relaxation ... both clear the 7-day gate"). The one control that *did* fire -- `ERR_PNPM_IGNORED_BUILDS` on `core-js` (`implementer.md:24`) -- is pnpm 11's **native default** behaviour for unapproved build scripts, not `strict-dep-builds=true` from the rc. That coincidence is what made the failure look like the policy working.

### Why this blocks

The bottom ten rows are the exact shape the quarantine exists to catch: one npm scope publishing nine sibling packages plus `memfs` in an eight-minute burst, landing in a lockfile roughly a day later. That is the TanStack/Mini Shai-Hulud propagation pattern `CLAUDE.md` documents, and the 7-day window is the only control on this machine that would have caught it. `webpack@5.110.3` is worse in blast radius: it executes with full developer privileges during `mise run check`, and now during CI's required `repo-wide` job.

I want to be precise about what I am and am not claiming. I am **not** claiming any of these 18 packages is malicious -- I have no evidence of that, and the odds are they are all fine. I am claiming the control that makes that question survivable was off, silently, while three separate documents recorded it as on. The lockfile now pins these versions by `integrity: sha512-...`, and `--frozen-lockfile` will faithfully reinstall exactly them on every gate run and every CI run, indefinitely. If one of them is bad, the pin is what makes it permanent.

The secondary problem: **CI has no `~/.npmrc` at all.** Even in a world where pnpm honoured the rc, `pages.yml` and `ci.yml` on `ubuntu-latest` would install with zero hardening. Nothing in the repo carries the policy across the machine/CI boundary.

### Fix

Put the policy where pnpm 11 actually reads it and where it travels with the repo -- `site/pnpm-workspace.yaml`, camelCase keys, committed:

```yaml
minimumReleaseAge: 10080
minimumReleaseAgeStrict: true
strictDepBuilds: true
verifyStoreIntegrity: true
strictStorePkgContentCheck: true
trustPolicy: no-downgrade
strictPeerDependencies: true
autoInstallPeers: false
packageManagerStrict: true
```

Then re-resolve from scratch (`rm -rf site/node_modules site/pnpm-lock.yaml && pnpm --dir site install`) and confirm either that the 18 packages resolve to older versions or that the install fails loudly and gets recorded. Do not relax `minimumReleaseAge` to make it pass; if a Docusaurus patch is unreachable inside the window, pin the previous patch and note it, per D3's own rule.

Note that `strictPeerDependencies: true` may surface real peer conflicts in the Docusaurus tree that `autoInstallPeers: true` has been papering over. That is the control working; resolve them rather than dropping the key.

Two things outside this branch's scope, for the lead:

- The dead `~/.npmrc` / `~/.config/pnpm/rc` policy affects **every pnpm 11 project on this machine**, not just `site/`. Worth a separate ticket.
- `plan.md:5,11` and `implementer.md:24,29` should be corrected in the same commit as the fix, per the repo's "when reality disagrees with the spec, reality wins" rule.

## A2 -- ADVISORY -- no `concurrency` group on the Pages workflow

`.github/workflows/pages.yml:1-16`

GitHub Pages allows one active deployment at a time. Two pushes to `main` in quick succession (or a push racing a `workflow_dispatch`) start two `deploy` jobs; one fails, and there is no ordering guarantee about which build wins. GitHub's own Pages starter workflow sets:

```yaml
concurrency:
  group: "pages"
  cancel-in-progress: false
```

`cancel-in-progress: false` rather than `true`, so a queued newer deploy waits instead of killing a publish mid-flight. Availability/correctness, not a security hole.

## A3 -- ADVISORY -- the `paths` filter misses files that change what gets built

`.github/workflows/pages.yml:6-10`

The filter is `docs/**`, `README.md`, `site/**`, `scripts/site-sync.sh`. These affect the built site and do **not** match:

| file | why it matters |
|---|---|
| `scripts/site-build.sh` | the script the `build` job actually runs |
| `mise.toml` | pins `node`/`pnpm` versions and defines the `site-build` task |
| `scripts/check.sh` | `run_repo_wide` calls `run_site_build` |
| `.github/workflows/pages.yml` | editing the workflow does not run it |

A change to any of these leaves the live site on the previous build with no signal. To be clear about the security framing the brief asked for: this **cannot** be used to skip a security control, because the build job contains none that a path filter could bypass -- it is a freshness/availability gap. `workflow_dispatch` is a working escape hatch, which is why this is advisory rather than blocking.

Cheapest fix: add `scripts/site-build.sh`, `mise.toml`, and `.github/workflows/pages.yml` to the list. Or drop the `paths:` filter entirely -- a ~30s build on every `main` push is not worth the footgun.

Related, harmless: `docs/**` matches `docs/phases/**` and `docs/progress.md`, which are never published, so those commits trigger a rebuild that produces byte-identical output. Wasted minutes, no risk.

## A5 -- ADVISORY -- the gate now depends on the npm registry, uncached, on two workflows

`scripts/check.sh:129-135,166-172`, `scripts/site-build.sh:14`, `.github/workflows/ci.yml:53-64`, `.github/workflows/pages.yml:20-30`

`run_repo_wide` now calls `run_site_build`, and `site-build.sh:14` runs `pnpm install --frozen-lockfile` unconditionally. So every local `mise run check` and every CI `repo-wide` run -- a **required** check on `main` -- reaches out to `registry.npmjs.org`.

On **integrity** the exposure is small and I want to say so plainly: `--frozen-lockfile` plus per-package `integrity: sha512-...` means a tampered tarball is rejected on arrival. The lockfile is a real control and it is doing its job. What it cannot do is vet a version *entering* the lockfile -- that was A1's job.

On **availability and cost** the exposure is real. Neither workflow caches the pnpm store; `mise-action`'s `cache: true` caches mise's own tool installs, not `~/.local/share/pnpm/store`. So CI re-downloads ~1151 tarballs on every run of both `ci.yml`'s `repo-wide` job and `pages.yml`'s `build` job. An npm outage now blocks every merge to `main`, including Go-only changes that have nothing to do with the site.

Suggested: add a store cache step keyed on `hashFiles('site/pnpm-lock.yaml')` to both workflows.
