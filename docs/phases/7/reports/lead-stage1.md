# Phase 7 lead report -- stage 1 (2026-09-02)

Attended stage 1, run with the released binaries (`cli/v0.1.0`, `mcp/v0.1.0`) against the registered dev app. Account: one membership, role `owner` -- these are IRL's real books, not a sandbox. **Write facts (G, H, I, J2, K, L, M, R) are DEFERRED unless Wes says otherwise**; read facts are authorized.

## Findings

1. **The CLI's default 44-scope set is rejected at consent** ("The requested scope is invalid, unknown, or malformed"). The scope names are correct (they match the 22 objects on https://www.freshbooks.com/api/scopes exactly; the spelling was verified against the rendered page). The cause is app registration: FreshBooks only lets an app request scopes enabled on it in the developer portal, and the dev app was registered in Phase 1 with only `user:profile:read` + `user:clients:read`. A second login with exactly those two scopes succeeded. Unknown scopes are not rejected at the authorize URL (a bogus `user:nonsense:read` returns the same generic page), only after login, so no unattended probe can enumerate an app's enabled scopes. **Corrections for the implementer:** `docs/getting-started.md` step 3 must say the requested scopes have to be enabled on the app, and the CLI's `auth login` help/docs should say the same next to `--scopes`; the default set stays (it is the documented full set) but the docs header's Security notes should name this failure mode and its fix.
2. **S1 CONFIRMED** -- `freshbooks auth login` end to end through the self-signed loopback: browser opened via `xdg-open`, the first callback attempt was rejected by the browser (`http: TLS handshake error from 127.0.0.1:<port>: remote error: tls: bad certificate` printed raw on the CLI's stderr), the user accepted the certificate, callback landed, `Login succeeded.`, credentials at `~/.config/freshbooks/credentials/default.json`, `auth status` shows `valid: true`, expiry 12h out, the two scopes. **Correction for the implementer:** the raw `http.Server` error line is expected on every first attempt and should be silenced or replaced by the existing one-line explanation (set `ErrorLog` on the loopback server to a discarding logger, or filter `tls: bad certificate`).
3. **S2 CONFIRMED** -- `freshbooks identity me -o json` returns a JSON list of memberships (keys `account_id`, `business_id`, `business_uuid`, `name`, `role`); `freshbooks clients list --account <id> --per-page 2 -o json` returns the `{items, page, pages, per_page, total}` envelope with 20 keys per client (`accounting_systemid`, `allow_late_fees`, `currency_code`, `email`, `fname`, `id`, `language`, `last_activity`, `last_login`, `lname`, `organization`, `p_country`, `pref_email`, `role`, `signup_date`, `updated`, `userid`, `username`, `uuid`, `vis_state`). No values recorded here.
4. **S3 CONFIRMED** -- `freshbooks-mcp serve --transport http --addr 127.0.0.1:18081`, `initialize` -> 200 with `serverInfo.name` `freshbooks-mcp`, `tools/call identity_whoami` with the bearer -> 200, no `isError`, result carries `id`, `email`, `first_name`, `memberships`. The server log contains no bearer or JWT fragment.
5. **Lib live smoke** (`TestLiveIdentity`, `-tags live`, `FRESHBOOKS_ACCESS_TOKEN` bridged from `freshbooks auth token` in the same shell) -- PASS.
